# Лабораторная работа №2: подготовка к сдаче

Пояснение к фактическим файлам `solver_openmp.c` и `solver_mpi.c`: алгоритм,
директивы, обмен данными и связь функций.

## 1. Суть лабораторной

Нужно решить систему линейных алгебраических уравнений:

~~~text
A * x = b
~~~

где:

- A — квадратная матрица коэффициентов размера N x N;
- b — вектор правых частей длины N;
- x — искомый вектор длины N.

Вариант №1 — **метод простой итерации**. Он начинает с начального приближения
x0 и несколько раз улучшает его, пока относительная невязка не станет меньше
требуемой точности eps.

Формула одной итерации:

~~~text
x(k+1) = x(k) - tau * (A * x(k) - b)
~~~

Здесь:

- x(k) — текущее приближение;
- A*x(k)-b — невязка, то есть насколько текущее приближение не удовлетворяет
  системе;
- tau — шаг метода; в программе используется 0.1/N;
- x(k+1) — новое приближение.

Итерации заканчиваются, когда:

~~~text
||A*x - b||2 / ||b||2 < eps
~~~

Евклидова норма вектора:

~~~text
||v||2 = sqrt(sum(v[i]^2))
~~~

Чем меньше eps, тем выше требуемая точность и обычно больше число итераций.

## 2. Тестовая задача

В лабораторной используется матрица:

~~~text
A[i][j] = 2, если i == j;
A[i][j] = 1, если i != j.
~~~

Программа поддерживает две модельные задачи.

### known

Искомое решение заранее известно:

~~~text
x[i] = 1
~~~

После этого вычисляется правая часть b = A*x. После решения программа
сравнивает найденный ответ с вектором из единиц.

### random

Заранее задаётся другое известное решение:

~~~text
u[i] = sin(2*pi*i/N)
~~~

Затем строится b = A*u. Правильный ответ — вектор u. Этот вариант нужен, чтобы
убедиться, что программа не работает только для вектора из единиц.

## 3. Что требуется в лабораторной

1. Реализовать метод простой итерации для чисел типа double.
2. Сделать MPI-версию:
   - матрица A делится между процессами по строкам;
   - близкие строки попадают в один процесс или в соседние процессы;
   - векторы x и b целиком находятся в каждом MPI-процессе;
   - исходные данные одинаковы при любом числе процессов.
3. Сделать OpenMP-версию.
4. Измерить время при 1, 2, 4, 8 и 16 worker.
5. Подобрать N и eps так, чтобы запуск на одном worker занимал не менее
   30 секунд.
6. Построить для MPI и OpenMP графики времени, ускорения и эффективности.
7. Проверить точность через относительную невязку и сравнение с известным
   модельным решением.

Формулы для отчёта:

~~~text
T(p) = время работы с p worker
S(p) = T(1) / T(p)
E(p) = S(p) / p
~~~

T — время, S — ускорение, E — эффективность. В идеале S(p) равно p, но в
реальности мешают обмен данными, синхронизация, кэш и накладные расходы.

## 4. MPI и OpenMP

MPI и OpenMP — не фреймворки в привычном смысле:

- MPI — стандарт и библиотека для обмена сообщениями между процессами;
- OpenMP — стандарт директив компилятора для параллельного выполнения циклов
  в нескольких потоках.

| Свойство | OpenMP | MPI |
| --- | --- | --- |
| Единица параллелизма | Поток | Отдельный процесс |
| Память | Общая | Раздельная |
| Передача данных | Не нужна для общих массивов | Явные вызовы MPI |
| Применение | Одно приложение на многоядерном ПК | Один или несколько компьютеров |
| Синхронизация здесь | Завершение цикла OpenMP | MPI_Allgatherv, MPI_Allreduce, MPI_Barrier |

В этой лабораторной MPI запускается на одном компьютере, но процессы всё равно
имеют раздельную память. Поэтому данные передаются через функции MPI.

## 5. Что распараллеливается

Самая дорогая операция каждой итерации:

~~~text
y = A * x
y[i] = sum(A[i][j] * x[j]), j = 0..N-1
~~~

Вычисление разных строк y[i] не зависит друг от друга. Поэтому строки матрицы
удобно распределять между потоками или процессами.

Также распараллеливается скалярное произведение:

~~~text
sum(v[i] * v[i])
~~~

Оно используется для расчёта нормы невязки.

## 6. OpenMP-версия

Файл: solver_openmp.c.

### Параметры

Структура Options хранит:

- n — размер матрицы;
- eps — точность;
- max_iter — предел числа итераций;
- random_solution — выбран ли режим known или random.

Функция parse_options разбирает аргументы командной строки.

### Хранение матрицы

Матрица хранится в одном массиве. Элемент A[i][j] располагается по индексу:

~~~c
a[(size_t)i * n + j]
~~~

Такое представление проще и эффективнее, чем массив указателей на строки.

### Заполнение матрицы

Функция fill_matrix создаёт A. Директива:

~~~c
#pragma omp parallel for collapse(2)
~~~

распределяет итерации двух вложенных циклов между потоками.

### Умножение A*x

Функция multiply вычисляет произведение матрицы на вектор. Внешний цикл идёт
по строкам:

~~~c
#pragma omp parallel for
for (int i = 0; i < n; ++i) {
    ...
}
~~~

Каждый поток получает несколько строк. Все потоки читают A и x, но каждый
записывает только свой элемент result[i], поэтому гонки данных нет.

### Скалярное произведение

В функции dot используется:

~~~c
#pragma omp parallel for reduction(+:sum)
~~~

У каждого потока своя частичная сумма, а OpenMP затем складывает их в sum.

### Основной цикл

В main:

1. Создаются матрица A, известное решение и правая часть b.
2. Вектор начального приближения x заполнен нулями.
3. На каждой итерации считается residual = A*x-b.
4. Проверяется относительная невязка текущего x. Если она меньше eps,
   решение найдено и цикл завершается.
5. Если точность ещё не достигнута, выполняется обновление:

   ~~~c
   x[i] -= tau * residual[i];
   ~~~

6. После окончания считается максимальная ошибка max(|x[i]-answer[i]|).

Iterations — число выполненных обновлений x. Converged сообщает, достигнута ли
точность. Если закончился лимит max_iter, программа возвращает код 2.

Время замеряется только для итерационного решения: создание матрицы и проверка
ответа в измерение не входят.

## 7. MPI-версия

Файл: solver_mpi.c.

### Начало работы MPI

~~~c
MPI_Init(&argc, &argv);
MPI_Comm_rank(MPI_COMM_WORLD, &rank);
MPI_Comm_size(MPI_COMM_WORLD, &processes);
~~~

- MPI_Init запускает MPI;
- rank — номер текущего процесса: 0, 1, и так далее;
- processes — общее число процессов.

Процесс с номером 0 печатает итоговые результаты.

### Деление строк

Функция make_layout строит:

- counts[p] — число строк у процесса p;
- offsets[p] — индекс первой строки процесса p.

Пример при N = 10 и трёх процессах:

~~~text
процесс 0: строки 0..3  (4 строки)
процесс 1: строки 4..6  (3 строки)
процесс 2: строки 7..9  (3 строки)
~~~

Строки всегда идут подряд, а размеры частей отличаются не более чем на одну
строку. Каждый процесс хранит только local_rows*N элементов матрицы.

Векторы x и b, напротив, полностью дублируются в каждом процессе. Это прямо
соответствует первому варианту MPI-реализации из задания.

### Локальное умножение

Функция multiply_local вычисляет только строки матрицы текущего процесса. Ей
нужен полный вектор x, поэтому x и хранится в каждом процессе.

### Сборка нового x

После итерации каждый процесс вычисляет только свой фрагмент new_x. Вызов:

~~~c
MPI_Allgatherv(new_x, ..., x, counts, offsets, ..., MPI_COMM_WORLD);
~~~

собирает части от всех процессов и передаёт итоговый полный вектор x каждому
процессу. Буква v означает, что процессы могут посылать разное число элементов.

### Глобальная норма

Каждый процесс находит частичную сумму квадратов только для своих строк.
Вызов:

~~~c
MPI_Allreduce(..., MPI_SUM, MPI_COMM_WORLD);
~~~

суммирует эти значения и передаёт общий результат каждому процессу. Так
вычисляется норма невязки всей системы.

### Время

Перед замером вызывается:

~~~c
MPI_Barrier(MPI_COMM_WORLD);
~~~

Она не даёт процессам начать замер до окончания подготовки у всех участников.
Полностью одновременный старт она не гарантирует. Время измеряется MPI_Wtime. Затем:

~~~c
MPI_Reduce(..., MPI_MAX, 0, MPI_COMM_WORLD);
~~~

оставляет на процессе 0 максимальное время. Это правильный результат, потому
что вычисление заканчивается только после завершения самого медленного процесса.

Собрать программы:

~~~powershell

~~~

~~~powershell

~~~

~~~powershell

~~~

три графика: время, ускорение и эффективность. На каждом показаны MPI и OpenMP.

## 10. Связь функций и порядок работы

OpenMP:

```text
main -> parse_options
     -> parallel + single (узнать фактическое число потоков)
     -> fill_matrix
     -> multiply(A, answer, b) -> dot(b, b)
     -> цикл: multiply(A, x, residual)
              -> residual -= b
              -> dot(residual, residual) -> проверка остановки
              -> x -= tau * residual
     -> проверка max(|x-answer|), печать, free
```

MPI:

```text
main -> MPI_Init -> MPI_Comm_rank / MPI_Comm_size
     -> parse_options -> make_layout -> fill_local_matrix
     -> локальное построение полного b -> MPI_Allreduce (норма b)
     -> MPI_Barrier -> MPI_Wtime
     -> цикл: multiply_local -> локальная невязка
              -> global_dot -> MPI_Allreduce (SUM)
              -> одинаковая у всех проверка остановки
              -> локальный new_x -> MPI_Allgatherv
     -> MPI_Reduce (MAX времени), MPI_Reduce (MAX ошибки)
     -> печать на rank 0, free, MPI_Finalize
```

В `multiply` используется `schedule(static)`: строки имеют одинаковую длину,
поэтому их удобно распределять заранее. В `fill_matrix` применяется
`collapse(2)`, а в `dot` — `reduction(+:sum)`. Локальная переменная `sum`
внутри тела цикла умножения принадлежит своей итерации. Массивы общие,
но потоки записывают разные элементы результата.

У циклов `parallel for` есть неявное ожидание завершения. Поэтому норма
не читается до расчёта всей невязки, а следующая итерация не читает
частично обновлённый x. `nowait` без перестройки алгоритма добавлять нельзя.
`omp_set_dynamic(0)` отключает динамическое уменьшение команды;
`single` записывает число потоков один раз. `OMP_NUM_THREADS` задаёт
запрошенный размер команды, вывод программы показывает фактический.

В MPI все процессы обязаны вызывать коллективные операции в одном порядке.
Общая норма позволяет им синхронно принять решение об остановке. Отдельный
`MPI_Barrier` внутри каждой итерации не требуется: алгоритм опирается
на зависимости данных и блокирующие коллективные обмены. Это не означает,
что любой коллективный вызов является универсальным барьером.

`counts` и `offsets` в `MPI_Allgatherv` измеряются в элементах `MPI_DOUBLE`,
не в байтах. Матрицу никто не рассылает: каждый процесс сам заполняет свой
блок. Полные b и answer строятся независимо, без генератора случайных чисел.
При P > N программа завершается с ошибкой.

## 11. Вопросы, которые могут задать

- Почему tau подходит? A = I + 11ᵀ, собственные значения 1 и N+1
  (при N=1 только 2); 0 < 0.1/N < 2/(N+1).
- Почему 263 обновления? Для known ошибка направлена вдоль вектора единиц;
  на каждом шаге умножается на 1 - 0.1(N+1)/N. При N=16000 и eps=1e-12
  порог впервые достигается после 263 обновлений.
- Почему random может сходиться медленно? Компоненты ошибки с собственным
  значением 1 сокращаются с множителем 1 - 0.1/N; это намного ближе к единице.
- Зачем хранить плотную A? По условию исследуется плотное умножение;
  специальное упрощение A*x = x + sum(x) в коде не применяется.
- Где главный расход? O(N²) операций умножения на итерацию. В MPI дополнительно
  передаются вектор и частичные суммы; в OpenMP есть расходы параллельных областей.
- Что именно измерено? Итерационный цикл, включая внутренние обмены/барьеры;
  создание данных и итоговая проверка не входят. Итоговый MPI_Reduce времени
  тоже находится после остановки таймера.
- Почему E иногда больше единицы? Это отношение единичных замеров со своим
  T(1), а не гарантия устойчивого сверхлинейного ускорения. Кэш, частота
  и фоновая нагрузка отдельно не контролировались.
- Что делать при b=0? Код заменяет нулевую норму b единицей, то есть проверяет
  абсолютную норму невязки. Начальное нулевое решение сразу подходит.
